# Verification

Verified November 11, 2026: **56 tests passed**, including an Ethereum fork at block **26,379,075**. No live transaction was sent.

```sh
uv sync --extra dev
uv run --no-sync vyper-grant --out build build
RUN_FORK_TESTS=1 uv run --no-sync pytest -q -s
uv build
```

The fork funds with real USDC and yvUSDC-1, withdraws exact USDC payments and impersonates the fixed Yearn voter to reassign an existing vote in the real controller. It clears a pre-start claim, performs automatic share capture and full-claim sales through the deployed gauge/minter and the fixed TriCRV pool (CRV → crvUSD), checks the rollover tail and captures before a revote. It verifies that the full minted amount was sold, existing multisig CRV remains untouched, and actual crvUSD output is conserved between both parties. It changes the Yearn receiver, verifies forwarding, resumes accumulation, and exercises governance's direct recovery of real vault shares. Post-programme proceeds return entirely to Vyper.

A separate local fork branch raises the gauge weight using impersonated governance until the actual gauge reaches its cap. The final claim is still sold even when the gauge reports killed. The escrow has no local cap accounting. No governance action leaves the fork.

Contract tests cover exact USDC draws from vault shares, yield and top-ups beyond the former 100k limit, share rounding, failed withdrawal rollback, whole-claim settlement, existing CRV/crvUSD/USDC balances, zero/partial/full Yearn shares, rounding, public idempotent checkpointing at the boundary and while paused, bounded missing-weight recovery, and sale permissions. A stale week is rejected before minting, and a claim above `max_crv` rolls back the mint and snapshot. The operator's crvUSD minimum scales with the actual minted CRV, so permitted claim growth cannot dilute the minimum per CRV; the minimum rolls back the swap if execution price worsens. Failures of mint permission, allowance, forwarding and return also roll back the snapshot and claim. Receiver changes preserve existing balances and can resume accumulation. Governance recovers shares and raw USDC before, during and after the programme, with sales paused and vault redemption blocked; unauthorized callers cannot recover funding. Tests retain coverage of rollover tails, zero-share settlement outside programme dates, gauge rate changes/caps, and independent claims.

Operations tests deploy proceeds before funding through the Python builder with mocks at the fixed mainnet addresses. They verify funding deployment without dates and proceeds setup, management and keeper operation without a funding address. They cover historical voter reads, a normal one-transaction sale with the encoded week, CRV quote and cap, checkpoint retries while paused, a closing sale below the normal minimum, the post-end cleanup, allocation without payments, manager withdrawals, pending nonces and a lost RPC response after a successful sale. The next pass reads fresh pending rewards instead of repeating the settled claim. Reports distinguish dated payments from weekly settlements, display active weeks without draws and warn about missing snapshots without depending on payments. CLI tests execute the prepared manager receiver-change batch and ychad.eth recovery batch; funding recovery works with no proceeds address or start date configured.

Both contracts compile with Vyper 0.4.3 and generated ABI/bytecode matches the sources. Both use the compiler's standard `IERC20` interface. Proceeds now settle directly in crvUSD: the second pool, its interface, address, approval and mock were removed. `quote` and `work` use 18-decimal crvUSD output/minimum amounts, and Sold names its output `crvusd`. The USDC and STABLE_POOL getters are removed. Existing tests verify that pre-existing crvUSD remains outside the split, unrelated USDC is untouched, output is conserved and forwarding failures roll back settlement; the fork verifies the real pool assets and return value. Reporting counts only crvUSD Withdrawn events as proceeds withdrawals and keeps USDC funding draws in their separate ledger. Python static checks, shell syntax and whitespace checks pass. The built wheel includes the compiled contracts and dashboard template. Desktop and 390px mobile layouts were inspected; the dashboard has no horizontal overflow or JavaScript errors.

Cooldown tests verify the 600-second default and hard floor, manager permissions, a shared interval across keepers, the exact eligibility boundary, and `canWork()` while paused. Failed sales leave `last_sale` unchanged. A public checkpoint can capture the new week while the cooldown is active. Operations tests verify that the keeper waits, that the final cleanup still bypasses the trade minimum after the cooldown, and that the CLI prepares a working manager cooldown update.

Funding tests verify that `draw(amount)` works before, during and after proceeds' programme dates and pays the fee burner by default. Loose USDC is left untouched and excluded from `assets()`; insufficient shares revert even when loose USDC is present. Only management can change the recipient; zero and self are rejected. CLI tests verify event-derived spending totals, payment timestamps and each payment's actual recipient. Proceeds tests validate its own constructor dates and demonstrate that a second week receives a fresh vote share without another payment, even after all funding is clawed back and vault withdrawals are blocked. The mainnet fork also skips the second-week payment while preserving Yearn's allocation. The dashboard shows weekly proceeds with a separate expandable payment history.

FundingEscrow is **57 lines** with a **1,678-byte** runtime. Its only mutable state is the recipient; draws write no escrow accounting storage. It has no dates, payment mapping, spending cap or seller dependency. ProceedsEscrow is **194 lines** with a **6,511-byte** runtime. It has no funding address, interface or payment checks. Its mutable state is weekly captured/share records, keeper permissions, the pause flag, Yearn's receiver, the cooldown and the last successful sale timestamp. No accrual baselines, inflation rates, caps, inventories, cursors or lifetime accounting totals remain. A weekly share is captured once; ordinary sales write only the cooldown timestamp in escrow storage.

These checks verify claim-week settlement, not exact earning-week attribution or compliance with the operating agreement. Closing sales are best effort, external claimers must stop, and substantial outages require reconciliation. `claimable()` uses eth_call to simulate the gauge checkpoint; `quote(amount)` is a separate view. Tests verify that quoting leaves the gauge untouched and claimable checkpoints without minting. No live deployment is recorded; fresh deployment is required. See [accounting](accounting.md) for the accepted assumptions.

Proceeds withdrawals use `withdraw(token, amount, recipient)`, restricted to the manager. Tests verify direct crvUSD payments, partial withdrawals, zero/self recipient rejection, failed-transfer rollback, withdrawals while paused and tokens that return no value. The Withdrawn event includes the destination, and withdrawals leave future-sale routing unchanged. The CLI test executes the generated withdrawal Safe batch without a funding address configured; reporting counts only crvUSD withdrawals. The mainnet fork withdraws the accumulated real crvUSD to the specified recipient. Funding recovery and governance clawback are unchanged.
